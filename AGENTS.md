# personal-homepage

A self-hosted start page. Pages hold items: links (tiles that open a new tab), apps (tiles that open the service
framed across the content area) and frames (a service shown inline at a set height). Home is always first and can't
be deleted. There is no database: pages are YAML files under `DATA_DIR`, served over GraphQL to a React app built
from the cubeui registry.

## Run

```
npm install
cp -r examples/data ./data     # optional sample pages
npm run dev                    # web on http://localhost:3000, API on :8787
npm run check && npm test
npm run build && npm start     # one process on PORT (default 3000) serving dist/
docker compose up -d --build   # pages in the homepage_data volume at /data
```

## Layout

- `server/core/`: config getters (`DATA_DIR`, `PORT`, `TRUST_PROXY`), the `defaults.ts` groups (`PAGE_LIMIT_DEFAULTS`
  is also served as `Query.pageLimits`), coded errors and preflight.
- `server/pages/`:
  - `page.ts`: the model and the `PageStore` interface. This is the seam for swapping the backend.
  - `page-input.ts`: zod validation of API input, run before any store.
  - `yaml-page-store.ts`: the YAML store.
  - `slug.ts`: slugs and item ids.
  - `widget.ts`, `widget-input.ts`, `widget-disk.ts`: the widget model, its API validation, and its YAML form.
- `server/widgets/`: fetching widget data. `widget-service.ts` is the cache (per page, item and settings hash),
  shared in-flight fetches and stale-on-error; `api.ts`, `rss.ts`, `weather.ts` are the fetchers;
  `secrets.ts` fills in `${env:HOMEPAGE_*}` / `${file:…}` and scrubs them back out of everything a fetch returns.
- `server/graphql/`: the SDL (`type-defs.ts`), resolvers (`schema.ts`), operation limits and the logger.
  `write-schema.ts` prints `schema.graphql`.
- `server/http/`: `createApp({ pages, dist })`, health and shutdown. `server/index.ts` only boots.
- `web/src/components/`: vendored cubeui and shadcn code. Don't edit it; reinstall with
  `npx shadcn@latest add @cubeui/<item>`.
- `web/src/core/`:
  - the typed GraphQL helper (`gql.ts`; its errors carry `extensions.code`)
  - the query client
  - the `Icon` to glyph map (`page-icons.tsx`)
- `web/src/pages/`:
  - `use-pages.ts`: one `['pages']` query. Every mutation writes the page or list the server returns into it.
  - `PageView`: tiles grid, inline frames, menus.
  - `AppView`: the full-area frame.
  - the page and item dialogs, and the client-side checks against `pageLimits`.
- `web/src/widgets/`: the widget card and its per-type views, `useWidgetData`, and the editor (`WidgetSettingsField`,
  holding a `WidgetDraft`) the item dialog shows for the WIDGET kind.
- `web/src/routes/`: TanStack file routes `/`, `/pages/$slug`, `/pages/$slug/apps/$itemId`. The tree is generated by
  `npm run codegen`.
- `tests/`: mirrors `server/`. Store tests run over a temp dir; `tests/http/app.test.ts` goes through `/graphql`.
- `examples/data/`: sample pages in the on-disk format.

## Rules specific to this repo

- **Nothing above the store touches files.** Resolvers and the web app use only `page.ts` types, so a database store
  can replace the YAML one in `server/index.ts` alone.
- **The store reads from disk on every call.** Hand edits show without a restart. Writes go through one in-process
  queue and are atomic (temp file, then rename).
- **A broken page file is skipped and logged, not fatal.** `find` reports it as NOT_FOUND with a message meant for
  the user.
- **Item URLs are http(s) only,** checked in `page-input.ts` and again when files are read. Frames load in this
  origin's page. Only a WIDGET may have no URL (`Item.url` is nullable for that); links and frames always have one.
- **A widget's secrets never leave the fetch.** References are stored and served as written; values are resolved in
  `server/widgets/secrets.ts` at fetch time, and every string a fetch returns (values, raw JSON, errors) passes
  through its `redact`. A new fetcher must take its strings through the same resolver. `tests/widgets` and
  `tests/http/widgets.test.ts` hold this.
- **Widgets fetch on view, never in the background.** No timers on the server.
- **No sign-in.** Keep it on a trusted network.
- **No Storybook stories yet.** The UI was checked with a scripted headless run. Adding stories is the next UI-test
  step.
